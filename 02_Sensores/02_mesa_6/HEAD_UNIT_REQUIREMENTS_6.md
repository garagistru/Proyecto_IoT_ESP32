# Требования к головному устройству
## Со стороны узла `mesa_datos` (ESP32-C6)

**Версия узла:** v3.3 FINAL  
**Тип узла:** кнопочный счётчик смен  
**Дата:** 2026-09-11

---

## 1. Общее

Головное устройство (ESP32-S3) выступает в роли **точки доступа Wi-Fi** и **HTTP-сервера** для датчиков. Узел `mesa_datos` обращается к нему по трём эндпоинтам:

| Метод | Путь | Назначение | Обязателен |
|---|---|---|---|
| `POST` | `/data` | Приём пакета завершённой смены | ✅ |
| `POST` | `/status` | Приём сигнала о смене состояния | ✅ |
| `GET` | `/time` | Выдача текущего времени | ✅ |

Базовый URL: `http://192.168.4.1` (шлюз по умолчанию в режиме AP).

---

## 2. Wi-Fi

### 2.1. Режим работы
- Головное устройство работает как **точка доступа (AP)**.
- SSID: `Mechanic`
- Пароль: `12345678`
- IP-адрес точки доступа: `192.168.4.1`
- DHCP-сервер должен выдавать IP подключённым датчикам.

### 2.2. Требования к стабильности
- Узел подключается **асинхронно** с интервалом 5 секунд при сбое.
- Таймаут подключения на стороне узла — 20 секунд.
- Головное устройство не должно «привязываться» к MAC-адресу узла — новый узел с любым MAC должен получить IP по DHCP.
- При потере Wi-Fi узел **накапливает данные в очереди** (до 20 смен) и отправляет их при восстановлении связи. Головное устройство не должно отклонять «старые» пакеты — время идёт в теле пакета.

---

## 3. Эндпоинт `POST /data`

### 3.1. Назначение
Приём **пакета завершённой смены** от узла. Пакет отправляется по одному раз в 30 секунд при наличии Wi-Fi.

### 3.2. Формат запроса

**Content-Type:** `application/x-www-form-urlencoded`  
**Body:** строка параметров, разделённых `&`.

| Поле | Тип | Обязательно | Пример | Описание |
|---|---|---|---|---|
| `mac` | string (12 hex) | ✅ | `84F703C12A44` | MAC-адрес узла без разделителей |
| `name` | string | ✅ | `mesa_6` | Имя станка (задаётся через `setname:`) |
| `actions` | int | ✅ | `145` | Количество нажатий за смену |
| `start` | string `HH:MM:SS` | ✅ | `08:15:00` | Время начала смены |
| `end` | string `HH:MM:SS` | ✅ | `16:45:30` | Время окончания смены |
| `time_source` | string | ✅ | `gateway` | Источник времени: `gateway` / `uptime` / `ntp` |
| `event_duration_s` | int (unsigned) | ✅ | `30630` | Длительность смены в секундах |
| `sensor_uptime_s` | int (unsigned) | ✅ | `86412` | Uptime узла в секундах |
| `boot_id` | string (8 hex) | ✅ | `3D8A29F1` | Уникальный ID текущей загрузки узла |

### 3.3. Пример тела запроса

### 3.4. Ожидаемый ответ

| Код | Значение для узла |
|---|---|
| `200 OK` | Пакет принят, узел удаляет его из очереди |
| Любой другой | Пакет остаётся в очереди, повтор через 30 сек |

Тело ответа узел **не разбирает** — важно только `HTTP 200`.

### 3.5. Требования к обработке

- Пакет должен быть **принят и сохранён** (в БД, файл, память) независимо от `time_source`.
- Если `time_source = uptime` — время в пакете условное (uptime узла, не реальное). Головное устройство должно это **помечать** при сохранении.
- Поле `boot_id` позволяет **группировать смены одной загрузки** — может использоваться для диагностики.
- Поле `event_duration_s` может дублировать `end - start` — это **не ошибка**, использовать как приоритетное (точнее, чем парсинг строк).
- Дубликаты пакетов возможны при нестабильной связи — рекомендуется **дедупликация** по комбинации `(mac, boot_id, start, end)`.

## 4. Эндпоинт `POST /status`

### 4.1. Назначение
Приём **сигнала о смене состояния станка** — начало или конец смены. Отправляется **немедленно** при переключении тумблера, без очереди.

### 4.2. Формат запроса

**Content-Type:** `application/x-www-form-urlencoded`

| Поле | Тип | Обязательно | Пример | Описание |
|---|---|---|---|---|
| `nombre` | string | ✅ | `mesa_6` | Имя станка (обратите внимание: `nombre`, не `name`) |
| `status` | string | ✅ | `abrir` | `abrir` — смена началась, `cerrado` — завершилась |

### 4.3. Пример тела запроса

### 4.4. Ожидаемый ответ

| Код | Значение для узла |
|---|---|
| `200 OK` | Сигнал принят (узел пишет в лог `STATUS 'abrir' OK`) |
| Любой другой | Узел игнорирует, повторов **нет** |

> ⚠️ **Важно:** сигнал `/status` **не буферизуется**. Если головное устройство недоступно, сигнал теряется. Реальное состояние смены восстанавливается по пакету `/data` при её завершении.

### 4.5. Требования к обработке

- Головное устройство должно **обновлять статус станка в реальном времени** (для отображения на TFT и в веб-интерфейсе).
- Статус `abrir` от узла должен означать «станок в работе».
- Статус `cerrado` — «станок остановлен».
- Имя в поле — `nombre`, не `name`. Это унаследовано от ESP8266-датчиков и **не должно переименовываться** без обновления прошивок.

## 5. Эндпоинт `GET /time`

### 5.1. Назначение
Выдача **текущего времени** для синхронизации часов узла. Узел запрашивает время при подключении к Wi-Fi и повторяет попытки каждые 30 секунд до успеха.

### 5.2. Формат запроса

Параметры не передаются.

### 5.3. Ожидаемый ответ

**Content-Type:** `application/json`

```json
{"hour":14,"minute":23,"second":7}

Поле	Тип	Диапазон	Описание
hour	int	0–23	Часы
minute	int	0–59	Минуты
second	int	0–59	Секунды
5.4. Требования к обработке
Парсер узла строгий: ищет подстроки "hour":, "minute":, "second": и читает число до , или }.

Порядок полей в JSON не важен, но ключи должны быть точно такими.

Лишние поля в JSON игнорируются — можно добавлять day, month, year без вреда.

Ответ должен быть валидным JSON (без BOM, без переносов внутри ключей).

Если головное устройство не имеет RTC или NTP — оно должно возвращать {"hour":0,"minute":0,"second":0} и узел переключится на uptime.

5.5. Использование времени на узле
После получения времени узел запоминает syncMs = millis().

Текущее время узла = startTime + (millis() - syncMs) / 1000.

При потере Wi-Fi — узел сбрасывает синхронизацию и переключается на uptime.

При восстановлении Wi-Fi — синхронизация повторяется автоматически.

Поле time_source в пакетах /data указывает, каким временем пользовался узел:

gateway — синхронизирован с головным (предпочтительно),

uptime — использовал свои секунды с момента загрузки (условное время),

ntp — реальное время от NTP (зарезервировано, пока не используется).

6. Требования к хранению данных
6.1. Минимальная схема
Поле	Тип	Обязательно	Примечание
id	auto	✅	Первичный ключ
timestamp	datetime	✅	Время приёма на головном (серверное)
mac	string	✅	MAC узла
name	string	✅	Имя станка
actions	int	✅	Количество нажатий
start	time	✅	Начало смены (условное/реальное)
end	time	✅	Конец смены
time_source	string	✅	gateway / uptime
event_duration_s	int	✅	Длительность в секундах
sensor_uptime_s	int	—	Для диагностики
boot_id	string	—	Для группировки смен одной загрузки
6.2. Индексы
(mac, start) — уникальный, для дедупликации.

(name, timestamp) — для выборок по станку.

(boot_id) — для группировки.

6.3. Хранение статуса
Отдельная таблица machine_status:

Поле	Тип	Описание
name	string	Имя станка
status	string	abrir / cerrado
updated_at	datetime	Время последнего обновления
При POST /status — UPSERT по name.

7. Обратная совместимость с ESP8266-датчиками (DHT11)
Головное устройство уже обслуживает ESP8266-датчики температуры. Требуется, чтобы новые эндпоинты /data, /status, /time не ломали существующие:

Узел	Тип пакета	Особенности
ESP8266 + DHT11	Температура/влажность	Поля: name, temp, hum — не конфликтуют
ESP32-C6 mesa_datos	Смена	Поля: mac, actions, start, end, boot_id и др.
7.1. Разделение по типу узла
Рекомендуется на головном устройстве различать узлы по набору полей:

Если в пакете есть actions — это смена, сохранять в shifts.

Если есть temp или hum — это датчик температуры, сохранять в sensors.

Если есть nombre и status — это сигнал состояния.

7.2. Унификация имён
Сейчас в /status используется nombre, а в /data — name. Это не должно переименовываться без синхронного обновления всех прошивок. Головное устройство должно поддерживать оба варианта.

8. Требования к производительности
Параметр	Требование
Одновременных подключений	≥ 20 узлов
Время ответа /data	≤ 500 мс
Время ответа /status	≤ 300 мс
Время ответа /time	≤ 200 мс
Потери пакетов	0 % при стабильном Wi-Fi
Пропускная способность	≥ 100 пакетов/минуту
9. Требования к стабильности
Головное устройство должно работать 24/7 без перезагрузок.

При сбое — авто-восстановление (watchdog).

При переполнении буфера приёма — не терять данные, а отклонять с 503 и понятным сообщением.

Логирование всех запросов в буфер обмена (Serial и/или файл).

10. Чек-лист приёмки
□ /data принимает все 9 полей, сохраняет в БД.
□ /status обновляет статус станка в реальном времени.
□ /time возвращает корректный JSON с секундами.
□ При потере Wi-Fi данные копятся в узле и отправляются после восстановления.
□ Дедупликация по (mac, boot_id, start, end) работает.
□ Существующие ESP8266-датчики продолжают работать.
□ Система выдерживает 24-часовой прогон без сбоев.
□ TFT-дисплей корректно отображает статус и последние смены.
11. Открытые вопросы (уточнить до реализации)
База данных — SQLite, PostgreSQL, MySQL? От этого зависит схема и миграции.

Дедупликация — на уровне БД (UNIQUE constraint) или в приложении?

Отображение времени — start/end показывать как есть или конвертировать в реальное с учётом time_source=uptime?

TFT-дисплей — что показывать: список активных станков, последние N смен, общую статистику?

Веб-интерфейс — фильтры по станку, периоду, источнику времени?

ESP8266-датчики — будут ли они модернизированы до того же формата boot_id?

Хранение времени сервера — использовать NTP на Ubuntu или полагаться на RTC ESP32-S3?
